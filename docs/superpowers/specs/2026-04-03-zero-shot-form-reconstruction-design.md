# 零样本表单重建设计文档

> 状态说明：本文档对应的零样本重建 CLI 方案已暂停，当前仓库主线已转向基于外部 `ocr_compact.json` 输入的 workbench 会话编辑流程。本文仅保留为历史设计记录，不再作为当前实施基线。

## 1. 背景与目标

本项目目标是在现有仓库基础上，实现一条“单张表单图片 -> OCR 结构化识别 -> 多模态大模型生成 HTML”的可运行链路，用于零样本表单重建。

首版聚焦以下目标：

- 输入仅支持单张表单图片
- 输出为可直接打开预览的单文件 HTML
- 视觉还原优先于语义完整性
- HTML 生成策略以绝对定位优先
- 前端 Next.js 首版只承担图片上传入口，不承担重建逻辑
- 后端需要提供可重复执行的命令入口，便于后续人工调试 prompt

本阶段的核心不是追求一次性达到最佳效果，而是尽快建立稳定的调试回路，使用户能够围绕 prompt 持续优化生成质量。

## 2. 范围

### 2.1 本阶段范围内

- 接收单张表单图片作为输入
- 调用 PaddleOCR Structure 产线，输出结构化 OCR 结果
- 将原图和 OCR 结果一起送入多模态大模型
- 由多模态大模型输出单文件 HTML
- 保存完整运行产物，支持用户复盘和手工调 prompt
- 提供 `Makefile` 命令，降低运行和调试成本

### 2.2 本阶段范围外

- 多页 PDF 或多页表单文档支持
- 自动 prompt 搜索或 prompt 自动优化
- 自动评分闭环与视觉相似度评价
- 多轮 agent 自反思修正
- 复杂的 HTML 自动纠偏系统
- 前端在线可视化调试台

## 3. 用户成功标准

以下条件全部满足时，视为本阶段目标完成：

1. 用户可以通过一条 `make reconstruct IMAGE=...` 命令跑通完整链路
2. 每次运行都会稳定产出 OCR JSON、发送给模型的 prompt、模型原始响应和最终 HTML
3. 生成的 HTML 可以被浏览器直接打开
4. 至少一张代表性表单图能够生成与原图大体对应的页面布局和关键视觉元素
5. 用户无需修改 Python 代码，只修改 prompt 模板即可继续调效果

## 4. 总体方案

本项目首版采用以下技术路线：

- 文档理解：PaddleOCR Structure
- 编排方式：Python + LangGraph
- 重建方式：多模态大模型直接根据“原图 + OCR 结果”输出 HTML
- 输出策略：单文件 HTML，自包含 CSS，可直接打开预览

在实现策略上，采用“主链路最短、调试产物完整保留”的原则：

- 优先快速打通从图片到 HTML 的最短路径
- 不设计过重的中间 DSL
- 保留足够的中间产物，给后续 prompt 调优留出空间

## 5. 架构设计

### 5.1 模块划分

后端按职责拆分为四个清晰模块。

#### 5.1.1 ingest

职责：

- 接收单张图片输入
- 做基础路径和格式校验
- 将输入复制到本次运行目录

输入：

- 本地图片路径，或由前端上传后交给后端的图片文件

输出：

- 标准化运行目录中的原图文件

#### 5.1.2 ocr_structure

职责：

- 调用 PaddleOCR Structure 产线
- 保存 OCR 原始结构结果
- 生成一份适合 prompt 使用的轻量整理结果

输入：

- 原始图片

输出：

- `ocr_raw.json`
- `ocr_compact.json`

#### 5.1.3 html_reconstruction

职责：

- 读取原图、OCR 结果和 prompt 模板
- 组装多模态模型请求
- 要求模型输出单文件 HTML
- 对模型响应做最小清洗并落盘

输入：

- 图片
- OCR JSON
- prompt 模板

输出：

- `prompt.txt`
- `model_raw.txt`
- `result.html`

#### 5.1.4 run_artifacts

职责：

- 管理一次运行的所有调试产物
- 提供统一目录结构，便于用户查看和比较结果

固定保留的产物包括：

- 原图
- OCR 原始输出
- OCR 精简输出
- 实际发送给模型的 prompt
- 模型原始响应
- 最终 HTML
- 元数据文件

### 5.2 编排方式

LangGraph 仅承担主流程编排，不承担复杂自治优化。

首版建议的节点顺序如下：

1. `load_image`
2. `run_ocr`
3. `build_prompt`
4. `call_model`
5. `write_result`

对应执行流为：

`load image -> run paddleocr structure -> build model input -> call multimodal llm -> normalize html -> write artifacts`

首版不引入自动重试决策节点，不做多分支 agent 协调。原因是当前阶段的目标是建立稳定调试回路，而不是构建复杂自治系统。

## 6. 目录结构设计

建议在现有仓库内按如下结构组织后端代码：

```text
backend/
  main.py
  app/
    pipeline/
      graph.py
      state.py
      nodes/
        load_image.py
        run_ocr.py
        build_prompt.py
        call_model.py
        write_result.py
    services/
      paddle_structure.py
      multimodal_llm.py
    prompts/
      reconstruct_html.md
  runs/
    <run-id>/
      source.png
      ocr_raw.json
      ocr_compact.json
      prompt.txt
      model_raw.txt
      result.html
      metadata.json
```

说明如下：

- `backend/main.py` 作为 CLI 入口，供 `Makefile` 调用
- `pipeline/` 只负责编排和状态传递
- `services/` 负责外部依赖封装，避免节点中混杂第三方调用细节
- `prompts/` 存放用户可直接修改的 prompt 模板
- `runs/` 保存每次执行的产物，支持回放和比对

## 7. 数据流设计

完整数据流如下：

1. 用户提供图片路径
2. 系统创建 `run-id` 并初始化运行目录
3. 原图复制到运行目录中
4. 调用 PaddleOCR Structure 并输出 `ocr_raw.json`
5. 从 OCR 结果中提取适合模型消费的精简结构，输出 `ocr_compact.json`
6. 读取 prompt 模板，将 OCR 结果拼入模板，生成 `prompt.txt`
7. 将“图片 + prompt”一起发送给多模态大模型
8. 保存模型原始输出到 `model_raw.txt`
9. 从模型响应中提取 HTML，做最小清洗
10. 输出最终 `result.html`
11. 写入 `metadata.json`，记录运行时间、输入路径、模型配置、状态等信息

## 8. Prompt 策略

首版 prompt 设计原则如下：

- prompt 必须外置为独立文件，不写死在 Python 代码中
- 每次运行都保留实际发送给模型的最终 prompt
- prompt 内容要明确要求“输出单文件 HTML”
- prompt 内容要强调“视觉还原优先，绝对定位优先”
- prompt 内容要限制模型不要输出解释文字或 Markdown 包裹

本阶段不做：

- prompt 自动版本管理
- prompt 自动搜索
- few-shot 样例选择系统

如果后续需要增强，可在当前文件化 prompt 的基础上继续扩展。

## 9. Makefile 设计

首版建议至少提供以下命令：

### 9.1 `make ocr IMAGE=...`

用途：

- 仅执行 OCR
- 用于检查 PaddleOCR Structure 输出质量

### 9.2 `make reconstruct IMAGE=...`

用途：

- 执行完整链路
- 产出最终 HTML

### 9.3 `make latest`

用途：

- 输出最近一次运行目录路径
- 便于用户快速找到调试产物

### 9.4 `make prompt-show`

用途：

- 输出当前 prompt 模板路径或内容
- 便于用户快速修改 prompt

之所以采用 `prompt-show` 而不是强依赖特定编辑器打开，是为了避免把使用方式绑定到用户本机环境。

## 10. 错误处理策略

首版错误处理只覆盖主链路中的关键失败点，保证失败后仍可定位问题。

### 10.1 图片输入错误

表现：

- 文件不存在
- 格式不支持
- 文件不可读

处理：

- 命令直接失败
- 输出清晰错误信息
- 不产生误导性的成功产物

### 10.2 OCR 失败

表现：

- PaddleOCR 调用异常
- 返回空结果
- 结果文件不可解析

处理：

- 保留原图和错误上下文
- 流程终止
- 不继续调用模型

### 10.3 模型调用失败

表现：

- 接口鉴权失败
- 请求超时
- 响应为空
- 返回内容不符合预期

处理：

- 保留 prompt 和原始响应
- 流程终止
- 输出明确错误提示

### 10.4 HTML 提取失败

表现：

- 模型输出混入解释文本
- HTML 结构不完整
- 提取后为空

处理：

- 优先做最小限度清洗
- 若仍无法得到有效 HTML，则流程失败
- 保留 `model_raw.txt` 供后续复盘

## 11. 测试与验证策略

本阶段测试策略以“冒烟可用”和“产物完整”优先，不做重型视觉回归。

### 11.1 单元测试

覆盖以下基础能力：

- 输入路径解析
- 运行目录创建
- prompt 拼装
- 输出文件路径生成

### 11.2 集成测试

通过 mock 模型调用验证：

- pipeline 能够完整执行
- 关键产物能够写入预期目录
- 错误情况下能够按预期停止并保留必要信息

### 11.3 手工验收

使用 1 到 3 张真实表单图片进行人工比对，重点关注：

- 页面整体布局是否对应原图
- 表头、分组、边框、输入框等关键视觉元素是否保留
- 是否能通过仅调整 prompt 改善效果

## 12. 阶段里程碑与暂停点

本阶段必须明确分为两个层次：

### 12.1 阶段一：打通可运行链路

达成条件：

- PaddleOCR Structure 已接入
- 多模态模型调用已接入
- `make reconstruct IMAGE=...` 可以跑通
- 运行目录中包含完整中间产物
- 最终可以输出单文件 HTML

### 12.2 阶段二：人工 prompt 调优前暂停

当阶段一达成后，实施需要暂停，并交由用户进行 prompt 调优。

也就是说，本次计划执行到以下状态即停止：

- OCR 输出稳定可见
- 模型输入 prompt 可见且可编辑
- 模型原始响应可复盘
- 最终 HTML 可打开预览

达到这里后，不继续默认实现以下能力：

- prompt 自动优化
- prompt 版本实验系统
- 视觉打分反馈闭环
- 自动多轮修正 agent
- 复杂规则后处理增强

这一暂停点是当前设计中的硬边界，用于保证实现工作与用户的手工 prompt 调试职责清晰分离。

## 13. 非目标与后续演进方向

本阶段不是最终形态，后续可按需要继续演进：

- 从单图扩展到多页文档
- 在 OCR 与模型之间加入更稳定的中间布局表示
- 增加表单语义识别与字段归类
- 引入自动评估指标
- 增加前端可视化对比与调试页面

这些内容不是本阶段承诺，不应进入当前实现计划。

## 14. 推荐实施结论

本项目首版建议采用“PaddleOCR Structure + 多模态模型单次生成 HTML”的最短主链路方案，并保留完整调试产物。

这样做的收益是：

- 以最少工程投入尽快获得可见结果
- 最大程度贴合当前“人工调 prompt”这一真实工作方式
- 为后续升级到更强的中间表示或自动修正能力保留演进空间

在此方案下，实施完成的标志不是“视觉效果已经最优”，而是“用户已经可以稳定地围绕 prompt 继续优化效果”。
