# 表单重建对话编辑工作台设计文档

## 1. 背景与目标

当前项目已经具备一条可运行的“图片 -> OCR -> prompt -> 多模态模型 -> HTML”重建链路，能够输出重建后的单文件 HTML，并保留调试产物。

接下来的目标不再只是离线生成 HTML，而是进入“在线连续修改”的工作阶段：用户需要在前端页面中一边查看当前重建后的表单，一边通过对话方式告诉大模型如何调整表单内容、字段语义和版面呈现。

本次设计的目标是为项目补出一个最小可用的“表单重建对话编辑工作台”，满足以下要求：

- 前端同时显示重建后的表单预览和智能体对话区
- 用户可以通过自然语言连续修改当前表单
- 系统保留多轮会话历史、每轮修改摘要和版本信息
- 系统维护一份可继续编辑的表单语义状态，而不只是一段 HTML
- 当前阶段支持字段语义修改与基础版面微调
- 当前阶段不强制将 LangGraph 作为主链路，但要为后续接入保留清晰边界

## 2. 范围

### 2.1 本阶段范围内

- 提供一个前端双栏工作台页面
- 基于现有重建能力创建表单编辑会话
- 新增后端 Web API，用于创建会话、发送修改指令、读取当前状态、回退版本
- 每轮对话返回：
  - 更新后的 `form_json`
  - 更新后的 `html`
  - 本轮 `change_summary`
- 保留多轮聊天历史与版本号
- 支持回退上一轮修改
- 对模型返回的结构化状态做基础 schema 校验

### 2.2 本阶段范围外

- 多用户协作编辑
- 持久化数据库存储
- 复杂权限与审批流
- 字段级手工拖拽编辑器
- 高保真像素级版面 DSL
- 自动 patch 合并引擎
- LangGraph 驱动的复杂多节点自治工作流

## 3. 用户成功标准

以下条件全部满足时，视为本阶段目标完成：

1. 用户可以基于一张已重建的表单创建一个编辑会话
2. 页面中同时能看到对话区和表单预览区
3. 用户输入自然语言修改后，右侧预览会自动刷新
4. 每轮修改都有清晰可读的变更摘要
5. 系统保存多轮历史，并支持回退上一轮
6. 系统内部维护 `form_json` 语义状态，但不要求其承担高保真版面

## 4. 总体方案

本次采用“语义状态驱动，HTML 做展示”的方案，而不是单纯让模型直接反复改 HTML。

具体做法如下：

- 使用 `form_json` 表示当前表单的可编辑语义状态
- 使用 `html` 表示当前可直接预览的重建结果
- 使用 `change_summary` 表示每轮修改的结构化摘要
- 用户始终通过自然语言发出修改意图
- 后端把当前上下文送给模型，模型返回新的 `form_json + html + change_summary`
- 前端默认自动应用结果，同时保留版本和回退能力

选择该方案的原因：

- 比“纯 HTML 连续修改”更可控，后续更容易做回退、差异展示和字段级编辑
- 比“一开始就构建高保真结构化 DSL”更轻，能更快跑通
- 能为后续引入 patch、工具调用和 LangGraph 编排保留清晰接口

## 5. 架构设计

### 5.1 分层结构

本阶段建议按四层组织：

#### 5.1.1 首次重建入口

职责：

- 从图片和 OCR 结果生成首版 `form_json + html`
- 作为编辑会话的起点

说明：

- 首版仍复用现有重建链路
- 只是将输出从“仅 `result.html`”扩展到“`form_json + html`”

#### 5.1.2 会话状态层

职责：

- 保存当前编辑会话的全部上下文
- 为每一轮后续修改提供稳定状态来源

说明：

- 后续多轮修改都基于当前会话状态继续推进
- 不重复从原图重新开始完整重建

#### 5.1.3 单轮编辑服务

职责：

- 接收用户当前轮指令
- 结合当前状态组织模型输入
- 产出新的 `form_json + html + change_summary`
- 通过校验后更新会话状态

说明：

- 当前阶段它可以是一个普通 Python service
- 不要求一开始就是 LangGraph 图编排

#### 5.1.4 前端工作台

职责：

- 左侧承载对话、历史和修改摘要
- 右侧显示表单预览和版本操作
- 提供自动应用和回退能力

### 5.2 前端工作台布局

本阶段已确认使用经典双栏布局（方案 A）：

- 左栏：对话区、历史记录、每轮修改摘要、输入框
- 右栏：表单预览、版本号、回退操作、查看本轮摘要

选择双栏布局的原因：

- 最适合“连续对话修改 + 即时预览”的工作方式
- 能兼顾聊天上下文与表单视觉对比
- 相比预览优先布局，更有利于追踪多轮编辑历史
- 相比三栏控制台，当前阶段更轻、更易实现

移动端建议降级为：

- 上下堆叠
- 或者“对话 / 预览”标签切换

## 6. 状态模型设计

### 6.1 `ocr_json` 的角色

`ocr_json` 继续作为初始重建的证据输入存在，但不作为后续编辑的主状态。

它的职责是：

- 描述 OCR 看到的原始结构
- 作为首版重建和必要时追溯问题的依据

它不适合直接承载多轮表单编辑，因为用户的对话指令是在修改“表单语义”，不是修改 OCR 识别结果。

### 6.2 `form_json` 的角色

`form_json` 是当前会话内的表单语义真相，用于承载：

- 字段定义
- 粗粒度分组
- 必填关系
- 字段类型
- 选项列表
- 基础布局提示

本阶段明确不要求 `form_json` 表达像素级版面。

### 6.3 `html` 的角色

`html` 是当前会话下的可见预览结果，用于：

- 右侧预览区直接展示
- 支持版面类指令的上下文参考
- 作为每轮修改后用户即时判断效果的载体

### 6.4 `change_summary` 的角色

`change_summary` 是每轮修改的结构化结果，用于：

- 在聊天区展示“本轮改了什么”
- 标识是否有警告或未完全满足的需求
- 为后续 diff、回退和 patch 化演进提供基础

## 7. `form_json` 最小 schema

本阶段建议 `form_json` 采用“字段语义 + 粗布局提示”的最小结构。

建议包含以下字段：

- `title`
- `description`
- `sections`
- `fields`

其中：

- `sections` 表示粗粒度区块，例如“基础信息”“联系方式”“审批区”
- `fields` 表示具体字段

每个字段建议最少包含：

- `id`
- `section_id`
- `label`
- `type`
- `required`
- `placeholder`
- `options`
- `layout_hint`

`layout_hint` 只保留少量高价值信息，例如：

- `width`: `full | half | third`
- `inline_with`: 另一个字段 id
- `emphasis`: `normal | strong`

示例：

```json
{
  "title": "客户登记表",
  "description": "",
  "sections": [
    {
      "id": "basic",
      "title": "基础信息"
    }
  ],
  "fields": [
    {
      "id": "name",
      "section_id": "basic",
      "label": "姓名",
      "type": "text",
      "required": true,
      "placeholder": "",
      "options": [],
      "layout_hint": {
        "width": "half"
      }
    }
  ]
}
```

## 8. `change_summary` 与历史结构

### 8.1 `change_summary`

建议每轮至少包含：

- `user_intent`
- `applied`
- `warnings`
- `unresolved`
- `touched_field_ids`

作用如下：

- `user_intent`：记录本轮原始意图
- `applied`：记录已成功应用的修改
- `warnings`：记录潜在风险或不稳定处理
- `unresolved`：记录未完全满足的部分
- `touched_field_ids`：记录影响字段

### 8.2 会话历史

每个编辑会话建议保存：

- `session_id`
- `version`
- `source_image_path`
- `ocr_compact_path`
- `current_form_json`
- `current_html`
- `messages`
- `turns`
- `latest_change_summary`

其中：

- `messages` 供模型上下文组织使用
- `turns` 供产品侧展示历史时间线使用
- `version` 每成功应用一轮递增

## 9. 对话编辑流程

单轮编辑的推荐流程如下：

1. 用户在左侧输入一句自然语言指令
2. 前端请求后端会话消息接口
3. 后端读取当前会话状态
4. 后端组织模型输入：
   - 当前用户指令
   - 最近会话历史
   - 当前 `form_json`
   - 当前 `html`
   - 必要的 OCR / 图片上下文
5. 模型返回：
   - 更新后的 `form_json`
   - 更新后的 `html`
   - `change_summary`
6. 后端校验结构
7. 校验通过后，写回会话状态并提升版本号
8. 前端自动刷新右侧预览，并在左侧插入本轮摘要

## 10. 字段语义修改与版面微调的分层

本阶段需要同时支持：

- 字段语义修改
- 版面微调类修改

建议分层处理：

### 10.1 字段语义修改

示例：

- “把联系电话改成必填”
- “新增备注输入框”
- “把日期改成下拉选择”

这类修改优先依赖 `form_json`，要求结果尽量稳定、可追踪。

### 10.2 版面微调类修改

示例：

- “把上面那个输入框调宽一点”
- “这一组改成两列”
- “标题小一点”

这类修改允许模型更多参考当前 `html`，并在可能的情况下把结果回写到 `layout_hint`。

本阶段接受这类修改的稳定性低于字段语义修改，但不能破坏整个会话状态主线。

## 11. API 设计

本阶段建议新增最小 API 集合：

### 11.1 `POST /api/sessions`

用途：

- 基于图片和 OCR 结果创建一个编辑会话
- 生成首版 `form_json + html`

返回：

- `session_id`
- `version`
- `current_form_json`
- `current_html`
- `initial_change_summary`
- `turns`

### 11.2 `GET /api/sessions/{session_id}`

用途：

- 读取当前会话状态
- 支持页面刷新后恢复

返回：

- `session_id`
- `version`
- `current_form_json`
- `current_html`
- `turns`

### 11.3 `POST /api/sessions/{session_id}/messages`

用途：

- 提交一轮自然语言修改指令

输入：

- `message`
- 可选 `client_version`
- 可选 `mode`

返回：

- `version`
- `assistant_message`
- `change_summary`
- `current_form_json`
- `current_html`

### 11.4 `POST /api/sessions/{session_id}/rollback`

用途：

- 回退上一轮或指定版本

返回：

- 回退后的 `version`
- `current_form_json`
- `current_html`
- `change_summary`

## 12. 前端交互设计

前端采用单页工作台：

- 左侧：
  - 会话标题
  - 当前版本信息
  - 聊天消息流
  - 每轮修改摘要
  - 输入框与发送按钮

- 右侧：
  - 当前表单 HTML 预览
  - 版本号
  - 回退上一轮按钮
  - 查看本轮摘要按钮

交互原则：

- 默认自动应用模型返回结果
- 用户无需每轮确认
- 但必须清楚看到本轮改动摘要
- 必须支持回退上一轮

## 13. 模型输出约束

由于 `form_json` 依赖模型生成，本阶段必须承认它不是天然可靠数据，因此至少增加三层约束：

### 13.1 固定 schema

先定义明确的 Pydantic 模型，不允许结构自由漂移。

### 13.2 输出校验

模型返回后必须校验：

- `form_json` 是否满足 schema
- `change_summary` 是否满足 schema
- `html` 是否为非空字符串

### 13.3 失败处理

本阶段建议采用中等约束：

- 校验失败时自动重试 1 到 2 次
- 重试仍失败则向前端返回错误，不更新当前状态

## 14. LangGraph 接入策略

本阶段不建议让 LangGraph 成为主链路依赖。

原因：

- 当前最缺的是 Web API、状态层和前端工作台
- 单轮编辑本质上仍然可以先视为一次受控模型调用
- 过早引入 LangGraph 会把基础设施问题和编排复杂度绑定在一起

推荐策略：

- 当前先实现一个独立的 `edit_turn_service`
- 它的输入是 `session_state + user_message`
- 它的输出是 `updated_form_json + updated_html + change_summary`

后续如果出现以下需求，再迁移到 LangGraph：

- 多步工具调用
- 自动修复和重试决策
- patch 合并
- 审批流
- 更复杂的上下文裁剪与状态分支

## 15. 实施顺序

建议按以下顺序推进：

### 15.1 第一步：后端状态与 API

- 新增 FastAPI 路由
- 新增会话状态模型
- 新增最小内存态会话存储
- 补出创建会话的初始重建能力

### 15.2 第二步：单轮对话编辑

- 新增消息接口
- 实现 `edit_turn_service`
- 模型每轮返回 `form_json + html + change_summary`
- 支持版本递增与回退

### 15.3 第三步：前端工作台

- 实现已确认的双栏布局
- 接入创建会话、发送消息、回退版本
- 用 iframe 或受控容器展示 HTML 预览

### 15.4 第四步：稳定性补强

- 加 schema 校验
- 加基础重试
- 增加版面类修改的 prompt 约束
- 为后续 LangGraph 替换预留接口

## 16. 测试策略

本阶段至少覆盖以下测试：

### 16.1 后端单元测试

- `form_json` schema 校验
- `change_summary` schema 校验
- 会话状态创建与版本递增
- 回退逻辑

### 16.2 后端接口测试

- 创建会话接口
- 发送消息接口
- 回退接口
- 非法模型输出时的错误路径

### 16.3 前端基础交互测试

- 页面能加载当前会话状态
- 发送消息后显示新摘要和新预览
- 点击回退后恢复上一版本

## 17. 风险与取舍

本阶段的核心取舍如下：

- 不要求 `form_json` 承担高保真布局，避免结构过重
- 接受版面类修改在当前阶段稳定性低于字段语义修改
- 不急于引入 LangGraph，以避免基础能力尚未稳定时架构过重
- 先用最小可用状态层把“对话编辑闭环”跑通，再决定后续是否升级到 patch 驱动或图编排

## 18. 本阶段结论

当前阶段最合适的方案是：

- 采用双栏工作台 UI
- 使用 `form_json` 作为编辑语义状态
- 使用 `html` 作为当前预览结果
- 使用 `change_summary` 承载每轮修改日志
- 默认自动应用，但支持回退与摘要查看
- 先实现普通 service 版单轮编辑，不把 LangGraph 作为首发主干

这条路线能够以最小复杂度建立“看得到、改得动、能追踪、可回退”的在线编辑闭环，并为后续 patch 化和图编排保留演进空间。
